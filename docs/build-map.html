Method

Build the ruler before the thing it measures

Phase 0 builds the fixture, the ground truth, the scorer, and a one-prompt baseline — and produces a number — before any agent exists. Every capability after that is one iteration: flip a flag in its stage preset, build the node, re-run the evaluation, write the changelog row. A feature is done when eval/results/<stage>/ exists, not when it works.

Runtime

What happens on a run

Verifier

How a claim is judged

The tailor drafts from profile.json. The verifier then sees the draft and the profile, and never the tailor's reasoning — so it cannot inherit the tailor's justification. Every document is checked twice over one shared, code-generated segmentation:

PassDoesWhy it exists
1 · segment codeMarkdown structure decides the claim units; role headings resolve to exp_2 by matching company namesAn LLM split moved between runs — 9 units then 6 — and silently dropped a fabricated employer
2 · extract LLMLabels what each unit asserts: tools, company, title, metrics, dates. Never sees the profileAn extractor that knows the answer shapes its extraction toward it
3a · rules codeAdjudicates every element against the frozen profile. The primary metricThree runs give byte-identical verdicts, so a stage delta is caused by the stage
3b · judge LLMThe PRD §5.8 verifier, keyed to the same unit ids. A cross-checkCatches claims that name nothing checkable

The five verdicts a claim can get

VerdictMeansRepair
supportedevidence places the tool in this role or project—
unplacedskills-line mention with nothing behind it — fine in a skills section, not in a bulleta gap question
misplacedreal evidence, wrong employer — Kafka-at-Amazondrop the line
declinedyou said you have not used itnone, ever
unsupportednot in the profile at alldrop the line

A sixth outcome, softened, applies to a whole unit that asserts nothing checkable. Counting it separately is what stops a resume scoring a perfect zero by turning vague — the failure mode a fabrication-only metric rewards.

Of your 61 evidenced tools, 45 may appear in a bullet today, 16 need a gap answer first. That gap is what iter4 measures: answer once where you used Kafka and it moves to supported permanently.

What running both paths found

"Led payments infrastructure work across a distributed billing platform."  →  rules: softened · judge: unsupported

The judge is right. The sentence names no tool, employer, or number, so element-based checking has nothing to hold. A fabrication written entirely in abstractions passes straight through a whitelist — and that is the register a fluent model reaches for. Neither path alone is the metric.

The H-1B lookup was specified as string matching, and string matching cannot do it. The PRD asked for normalize → exact → fuzzy ≥ 90 → "does not sponsor". Run against the real USCIS export, that broke three different ways inside fifteen postings, so it was rebuilt as deterministic retrieval plus an agent that can search — the counts stay facts read from the file, the choice of which legal entity is this company becomes a judgement.

  1. The legal name is not the brand name. SpaceX files as SPACE EXPLORATION TECHNOLOGIES CORP, which shares no token with "SpaceX" — the fuzzy shortlist is ISPACE INC and DSPACE INC. No threshold anywhere retrieves it, and the strict version reported "no petitions found" about a company with thirteen.
  2. Fuzzy ties span unrelated companies. ABRIDGE AI INC (CA/PA, health AI) and ABRIDGE INFO SYSTEMS INC (MA, IT staffing) both score exactly 100; extractOne picks by list order. The agent breaks the tie on filing state against the posting's "SF Office".
  3. Normalization collides distinct employers. Stripping technologies, us and inc maps COHERE US, INC. (6 approvals) and COHERE TECHNOLOGIES INC (0, a wireless company) onto one key — so even an exact hit named the wrong company and summed two firms' filings.

Result: 15/15 employers identified correctly across 20 searches, at roughly double the cost per posting. The case that matters most is jd_12 OnePay, absent from all 44,298 rows: the agent searched six times and still returned no entity, which is the behaviour a project measuring fabrication has to get right.

Nothing is dropped, and that is correct. No company in the fixture is a non-sponsor — fourteen of fifteen actively file, and OnePay is absent, which is unknown rather than no. Dropping on absence would have removed a posting labelled most_matched. The two postings that genuinely cannot hire her, SpaceX and Mach, are caught by triage reading the ITAR and clearance text.

The node was decorative, and fixing that did not move the number. As first built its verdict reached only the digest — triage_prompt never saw it — so iter2 doubled cost while changing no label. It now feeds triage as evidence, guarded by an instruction that filing history never overrides a role-level bar. That guard is the whole risk: "SpaceX likely sponsors, 13 approvals" argues against the skip SpaceX requires. It held, and the agent said why unprompted — "SpaceX's H-1B filing history is irrelevant here; export-control and clearance requirements govern this specific role". But triage stayed at 73.3% either way, cells reshuffling inside the noise band. The node buys correct employer identification and a digest column at 2× cost, and has not yet been shown to improve a label.

Two postings flap between runs, so a 6.7-point move is not a result. Re-running iter1 with no change to the triage node scored 66.7% where it had previously scored 73.3% — the whole difference is jd_15 Cohere flipping between skip and less_matched on seniority. With fifteen items one posting is 6.7 points, and at least two are unstable, so differences under ~13 points on this fixture are reported but not claimed. iter2's triage number moved for exactly this reason and the changelog says so: the H-1B node answers an employer-level question and is forbidden from touching role eligibility, which is triage's.

Self-verification removes nothing, and the failure mode is worse than "barely helps". On the five postings iter3 and iter3a both produced, fabrications were 0.20 either way — one each, identical per posting. On jd_01 self-review did not fix the fabrication, it swapped it: the hedge "Flask-style web services via FastAPI" went away and "Backend engineer", a title the profile does not contain, took its place.

The self-assessments are the evidence. On jd_03 the model reported "No fabricated claims … All metrics, dates and tool-to-role attachments" verified; on jd_10, "kept all tools inside the exact roles/projects they belong to". A model auditing its own draft, with its own reasoning still in context, ratifies it. That is why iter3b's verifier gets its own node, its own instruction, and no sight of the tailor's context — and why this stage stays in the table with its evidence rather than being deleted.

Read iter3b's zero with suspicion — we do. The pipeline verifier and the harness scorer share code by design (PRD §5.8). The scorer counts what the rules path rejects, and the verifier node now deletes precisely that, so 0 fabricated claims is close to guaranteed and is not evidence the stage works. It proves only that the loop terminates and never ships a rejected claim.

The real result is that content held. The failure to fear was reaching zero by gutting the resume — iter3a's mistake in a new costume. On the five postings iter3 and iter3b both produced, supported claims per document went 24.0 → 23.6, flat. jd_01 ended with more supported claims than before (22 → 24) once its Flask hedge was removed.

Two apparent regressions, both attributable and neither the verifier's: softening rose because four units are bare school headings that assert nothing checkable (a formatting change), and coverage fell entirely on jd_09 — which needed zero revision rounds, so the verifier never touched it. Cost: wall-clock doubles to 79.6 s/JD. And strip_units, the "cut the lines in code" path, has been unit-tested but never fired in a real run.

What the baseline actually got wrong

Three failures, in the order the iterations attack them:

  1. It fabricates exactly where the posting asks for something absent from the profile. Canonical wants Flask and the resume claims Flask; DoorDash wants Swift and it appears as "Swift: currently learning"; Zynga wants C# and Unity and both appear. It also placed PostgreSQL inside the Amazon role — a NextRound tool — and put Hibernate in a bullet when it is a skills-line mention.
  2. It cannot see sponsorship. SpaceX (ITAR) and Mach (export-control) were both labelled less_matched rather than skipped, so effort goes to jobs that cannot hire her.
  3. It is too conservative. Of six author most_matched it agreed on three and downgraded three; it also downgraded two of three skips.

The baseline number moved 8.13 → 5.53 → 1.8 → 1.6 before it settled, and nothing about the baseline changed. Each drop removed a false reject in the verifier: an exact-match date rule was rejecting every employment heading in every document because a resume writes "May 2025 – Aug 2025" where the profile stores 2025-05; then Kubernetes (EKS), MySQL/RDS, plural tool names, and degree-plus-school credentials. The rules-vs-judge disagreement is what surfaced it — 61.8% agreement was the signal, and it is 86.7% now. Fixing stopped at 1.6 rather than chasing zero: GCP and Ubuntu are still counted, and continuing would be fitting the scorer to flatter the result. The primary metric has a measured false-reject floor, and the README says so.

Open

Still on the table

  • 16 self-study tool entries widen what a resume may claim. They are in because your resume names them; the placement rule keeps them honest.
  • One location per tool. ToolEvidence.where holds a single id, so a tool used twice leans on the role's own tools list.
  • Test fixtures can flatter the scorer. They were written to the failure modes. The real test is the baseline, on documents nobody wrote to be caught.
  • Cut order if Sunday runs short: iter5 → short answers → profile update agent → the H-1B agent (falling back to exact-match retrieval only, which the iter2 row shows is wrong on three of fifteen). Never cut: verifier node, eval harness, stage presets, non-interactive mode, changelog evidence, trajectories, onboarding agent.
